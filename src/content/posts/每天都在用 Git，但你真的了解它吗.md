工作中天天用 Git，add、commit、push 闭着眼睛都能敲。但有几个问题一直卡着我：checkout 到某个提交之后，提示的"分离头指针"是什么意思？变基之后为什么非要强制推送？不小心删掉的提交还能找回来吗？为什么有的仓库 clone 特别慢？

这次集中查了些资料，也参考了几篇讲 Git 原理的好文章，把自己的疑问和学到的东西由浅入深整理成这篇笔记，分享出来供大家参考，有不对的地方欢迎指正。

## 一、先说 Git 和别的版本控制有什么不一样：快照，而不是差异

很多老的版本控制系统（SVN、CVS）存的是差异：保存一份初始版本，之后每次只记改了什么。想看某个历史版本，要从头开始把差异一个个应用上去。

Git 换了个思路：每次提交在概念上都保存项目在那一时刻的完整快照。文件没变，就直接引用之前存过的那份内容，不再存第二份。

这个选择带来几个直接的好处：切换到任意历史版本，直接读那个版本的快照就行；比较两个版本，就是比较两个快照；创建分支，只是创建一个指向某个快照的指针。

这里先留一个问题：每次都存完整快照，体积不会爆炸吗？先记下来，第六节再说。

## 二、Git 底层存了什么：四个对象，一张图

Git 仓库的核心在 .git 目录里。所有内容，文件内容、目录结构、提交信息，都以"对象"的形式存在对象数据库里。每个对象用内容本身的哈希值当名字。

内容寻址有四个特点，我觉得这是理解 Git 的钥匙：

- 相同内容只存一份：不管一个文件在多少个提交、多少个目录里出现过，内容一样，哈希就一样，库里只有一份
- 内容不可变：对象的名字由内容决定，改了内容就是一个新对象，老对象永远不会被改
- 完整性校验：读一个对象的时候可以重新算哈希，和名字对一下，数据坏了马上能发现
- 比较快：判断两个对象是不是一样，只用比哈希，不用比内容本身

四种对象是这样的：

- blob：文件内容，不含文件名
- tree：目录，一条条记录（模式、类型、哈希、文件名），可以嵌套
- commit：一次提交，指向一个 tree，带父提交、作者、提交者、说明
- tag：给某个对象起个带说明的名字

一个小例子能把这张图说清楚。项目里有一个说明文件和一个源代码目录，改了一个源文件再提交，会发生什么：

- 改过的文件产生一个新的 blob
- 源代码目录变了，产生一个新的 tree
- 根目录也变了，产生一个新的根 tree
- 生成一个新的 commit，指向新根 tree，父提交是上一次提交
- 说明文件和没改过的源文件，直接复用原来的对象，一点新存储都不产生

所有提交通过父提交连在一起，形成一张有向无环图（DAG），这就是版本历史。

还有一个细节：commit 里作者和提交者是两个字段。作者是最初写这些修改的人，提交者是把修改提交进仓库的人。大多数时候是同一个人，但在变基、cherry-pick 之后，提交者会变，作者不变。

动手验证一下。Git 的日常命令都是"高层命令"，底下还有一组"底层命令"可以直接操作对象数据库。不用全记住，跑两条就能感觉到：

```bash
echo "Hello World!" | git hash-object -w --stdin
git cat-file -p <哈希值>
```

第一条把内容写进对象库，返回它的哈希；第二条按哈希把内容取回来。甚至不用 git add、git commit，也能用 update-index、write-tree、commit-tree 手工攒出一次提交。日常命令本质上就是这些底层操作的组合和封装。

## 三、分支、HEAD 与引用：指针而已

对象靠哈希访问，但没人能记住 40 位哈希。引用就是给哈希起的人类可读的名字，存在 .git/refs 下面。

分支在 Git 里只是一个指向某个提交的可移动指针。底层就是一个文件，文件名是分支名，内容是提交的哈希。新建分支就是新建一个几十字节的文件，所以 Git 的分支又快又便宜。

HEAD 是个特殊引用，表示"当前所在的位置"。通常它是个符号引用，指向当前分支；提交时 Git 通过 HEAD 找到当前分支，再移动分支指针。

分离头指针（Detached HEAD）：直接 checkout 某个提交而不是分支时，HEAD 里直接就是提交的哈希，不指向任何分支。这时候也可以正常改、正常提交，但新提交没有任何分支指向，一旦切走就很难再找到。所以想保留的话，切走之前先建个分支。

引用日志（reflog）是 Git 的"安全网"：它记着每个引用在本地的每一次移动。reset、rebase 之后"丢"了的提交，只要还没被垃圾回收，都能用 git reflog 找到哈希，再建个分支指回去。注意 reflog 只在本地，不会被推送或克隆，里面的条目过一段时间也会过期。

## 四、三个区域：暂存区到底是什么

理解日常操作，要先分清三个区域：工作目录、暂存区（也叫索引）、仓库。

暂存区底层是 .git 里的一个二进制文件，记录了一个扁平的文件列表：每个文件的路径、对应 blob 的哈希、模式，还有文件大小、修改时间这些元数据。它描述的其实就是"下一次提交的 tree 长什么样"。

git add 的时候，Git 就把文件内容作为 blob 写进了对象库，并在暂存区里更新了这个文件的哈希。也就是说，add 的时候内容就已经进库了。git commit 的时候，Git 按暂存区的列表拼出 tree，再包成 commit，最后移动当前分支的指针。

git status 是在比什么：

- HEAD 的 tree 和暂存区不一样的文件：已暂存，等着进下一次提交
- 暂存区和工作目录不一样的文件：改了但没暂存
- 在工作目录里、但不在暂存区、也没被忽略的文件：未跟踪

Git 判断文件变没变，不会每次都重新算所有文件的哈希，而是先比大小和修改时间这些元数据，没变就认为没改过，大仓库里 git status 才快得起来。

理解了三个区域，reset 的三种模式也就不难了：

- --soft：只移动分支指针，暂存区和工作目录不动
- --mixed（默认）：移动指针，暂存区回到目标提交的样子，工作目录不动
- --hard：指针、暂存区、工作目录全回到目标提交，未提交的修改直接丢掉

暂存区的好处是能精确控制每次提交放什么：工作目录里同时改了好几处不相关的东西，可以分批 add，拆成几个逻辑清晰的提交，甚至只暂存一个文件里的一部分修改。

## 五、合并与变基：同一个目标，两种历史

合并：三方合并

两个分支要合在一起，Git 会先找它们的合并基础（merge base），也就是最近的共同祖先，然后对每个文件比较三个版本：

- 只在一边改过的文件，用改过的版本
- 两边改成一样的内容，用这个内容
- 两边都改了但改的地方不一样，行级别自动合并
- 两边改了同一个地方，冲突，人工解决

为什么非要一个合并基础？只比两个分支的最新版本，分不清差异是谁引起的。比如某一行在一个分支里有、另一个分支里没有，可能是这边加的，也可能是那边删的。有了合并基础，就知道它原本在不在。

快进合并：如果要合进来的分支是当前分支的直接后代，当前分支直接把指针往前移就行，不用新建提交。

合并提交：如果两边都有各自的新提交，合并后会新建一个合并提交，它有两个父提交，分别指向两边的最新提交，提交图里就记下了两条开发线在这里汇合。

还有一个有意思的设计：Git 并不显式记录文件的重命名。提交里只记快照，不记"某个文件被重命名"这种操作。比较差异和合并的时候，Git 靠内容相似度推断重命名：一个文件从某个路径消失，同时在另一个路径出现了一个内容高度相似的文件，就认为是重命名，默认相似度超过一半就算。所以重命名文件和大幅改内容，最好分在不同的提交里。

变基：把提交"搬"到新的基础上

变基是另一种整合方式：把当前分支上的一系列提交，"移动"到另一个分支的最新提交之后，历史看起来就像是在对方最新状态上开发的一样。

但对象是不可变的，提交不可能真的被移动。变基实际做的是：

- 找到两个分支的合并基础
- 找出当前分支上合并基础之后的所有提交
- 把当前分支的位置重置到目标分支的最新提交
- 把找出来的提交一个个重新应用过来，每应用一个就新建一个提交

新提交和原来内容一样、说明一样、作者一样，但父提交不同，哈希完全不同，是全新的提交对象。原来的提交没被删，只是不再被分支引用，还能通过 reflog 找到。

变基和合并，最后代码内容通常是一样的，区别在历史的形态：合并保留了并行开发的真实面貌，但分支多了历史会变乱；变基产出一条直线历史，好读、好审查、好二分查找问题，但改写了历史。

黄金法则：不要对已经推送、可能被别人用的提交做变基。别人已经基于那些提交开发了，你一变基一强制推送，对方再同步时就会看到两组不同的提交，相同的修改出现两次，或者一堆看不懂的冲突。这也是变基后要强制推送的原因：远程分支指向的提交已经不是本地历史的祖先，普通推送会被拒绝。非要强制推送时，用 --force-with-lease，它只在远程分支还在你预期的位置时才覆盖。

cherry-pick：把另一个分支上的某一个提交拣过来，在当前分支上新建一个内容相同的提交。变基本质上就是对一系列提交依次 cherry-pick。

## 六、存储与打包：快照不等于浪费

回到第一节留的问题：每次都存完整快照，体积不会爆炸吗？

新对象创建时是"松散对象"：内容压缩后单独存一个文件，用哈希前两位当子目录名。Git 定期把松散对象打包成包文件（packfile）：排序让相似对象相邻，把其中一个存成相对另一个的差异（增量对象），再统一压缩。

关键的一点：差异压缩纯粹是存储层的优化，和对象模型、提交历史无关。增量对象的基础不一定是同一个文件的上一个版本，可以是任意内容相似的对象；而且 Git 通常让较新的版本存完整内容、较旧的版本存差异，因为新的更常被访问。对使用者来说，对象永远是完整快照，打包是透明的。

git gc 会在适当的时候做这些事：打包松散对象、合并多个包、删除不可达对象（从所有引用出发到不了的对象，过一段宽限期后删除）。用 git verify-pack -v 可以看包里装了什么。

大仓库还有更多优化：提交图文件（预先算好提交图结构，查历史、找合并基础更快）、稀疏检出（只检出部分目录）、部分克隆（先不下载历史里的大文件，用到再取）、浅克隆（只取最近几次提交）。这些都是在"快照"模型之上的工程优化。

## 七、大文件、diff 与模型权重

Git 是为文本设计的：源代码、Markdown、配置文件、JSON、YAML。文本按行组织，改动通常只涉及几行，快照加增量压缩才能发挥作用；文本可读，冲突能手动合并。

git diff 是按行比较文本，默认 Myers 算法，也可以换 histogram、patience、minimal。能对比任意两个快照：工作区对暂存区、暂存区对提交、提交对提交、分支对分支。

二进制文件出现 NUL 字节就被判定为二进制，diff 只会说 Binary files differ。可以 git diff --text 强制按文本处理，或者在 .gitattributes 里配 textconv，让 Git 先把文件转成文本再比。

大文件不适合 Git 的三个原因：

- 每版都是一份完整的新 blob，二进制几乎无法增量压缩
- 每次 clone 都要下载全部历史
- 没法合并，冲突只能二选一

GitHub 的限制可以参考：单个文件超过 100MB 会警告并拒绝推送，仓库建议控制在 1GB 以内。标准解法是 Git LFS：仓库里只存一个百来字节的指针文件，真正的内容存在 LFS 服务器上，checkout 时按需下载。

```bash
*.psd filter=lfs diff=lfs merge=lfs -text
*.zip filter=lfs diff=lfs merge=lfs -text
```

模型权重：一开始我也觉得奇怪，权重文件动辄几个 GB 到几百 GB，按上面的说法根本不适合 Git。后来搞明白了：它们用的不是纯 Git，而是"Git 加 LFS"。Hugging Face Hub 上每个模型仓库本质上就是一个 Git 仓库，但权重文件（.safetensors、.bin）走的是 Git LFS。git clone 一个模型仓库时，拉下来的是指针文件，真正的权重是 LFS 按需下载的。准确的说法是：用 Git 管理模型的版本结构（配置、代码、README、指针），用 LFS 管理权重本体。

还有几个细节：

- safetensors 格式本身很干净：头部是 JSON 元数据，数据区可内存映射，加载快。但这解决的是加载问题，不是 Git 存储问题。
- 权重更新频率低，模型一般按版本发布，不像代码那样天天改；小文件比如 LoRA 适配器只有几 MB，直接进纯 Git 也没问题。
- Hugging Face 收购的 Xet 做了分块级去重：把大文件切成小块按内容哈希去重，同一底座的不同微调版共享大量块，比 LFS 整文件级去重更省。

## 八、分布式与远程仓库：同步、SSH 与工作流

远程仓库就是托管在别处的同一个项目的仓库，本地可以配多个，每个有个名字和地址。

fetch、pull、push 各干什么：

- fetch：从远程下载本地没有的对象，更新远程跟踪分支。只动远程跟踪分支，不动本地分支和工作目录，是安全操作
- pull：先 fetch，再把远程跟踪分支合并（或变基）到当前分支
- push：把本地提交和相关对象传上去，请远程移动分支指针。默认只接受快进式更新，新提交必须是远程分支当前提交的后代，这样就不会丢掉远程已有的提交。别人先推了，你的推送会被拒绝，先 fetch 整合再推

同步时怎么决定传哪些对象？双方先交换各自引用指向的提交，客户端告诉服务器自己已经有了哪些提交，服务器找出共同拥有的提交，再算出对方需要的、对方还没有的全部对象，打包发过去。因为对象是内容寻址的，双方不用传内容比对就知道对方有没有某个对象。

SSH 是怎么回事：Git 的 SSH 就是标准的 SSH。git clone git@github.com:xxx 时，Git 在本地启动一个 ssh 进程去连对方，认证方式和登录服务器一模一样。区别在认证成功之后：Git 服务器执行一个受限命令，拉取时是 git-upload-pack，推送时是 git-receive-pack，一般通过 authorized_keys 的 forced command 或 git-shell 限制，登录不进去 shell。真正的 Git 数据传输协议（pack 协议）跑在 SSH 通道里面。SSH 只是传输层，Git 也支持 HTTPS、本地路径、git://。

本地仓库和远程仓库的区别：

- 远程通常是 bare 的，只有 .git 里的内容，没有工作区；本地是非 bare 的
- 远程是同步点、备份和协作枢纽，但不是架构上的权威；本地历史是完整的，远程丢了可以从任何一个 clone 重建
- origin/main 只是"上次同步时对方 main 的位置"这个缓存，不是实时状态
- 分支保护、Deploy Key 读写权限是托管平台的策略，不是 Git 本身的概念

工作流：Git 的灵活性能支持好几种协作方式，集中式（所有人都和一个中央仓库同步）、功能分支（每个功能独立分支，做完审查合并）、派生（开源项目常见，先 fork 再提合并请求）、主干开发（小步快跑直接合主干）。没有哪种是"标准答案"，看团队习惯。

## 九、Git 和对象存储的版本管理有什么不同

两者都叫"版本管理"，但管的东西和目的完全不同。先说共同点：都是"只追加、不改写"的历史。Git 的对象一旦写入就不可变，新版本是新对象；对象存储开版本管理后，每次覆盖也是产生一个新版本，旧版本原样保留。两者都靠保留历史来防误删、防覆盖。但相似点基本到此为止。

区别一，版本化的单位不同。Git 管的是一棵树：一次 commit 是整个项目在某一时刻的完整快照，多个 commit 连成有向无环图，有分支、有合并。对象存储管的是单个对象：一个 key 有一条线性的版本链，每次 PUT 产生一个新版本。不同 key 之间没有任何关系，更没有"这次提交改了哪几个文件"这种整体状态的概念。

区别二，版本是人创建的，还是自动产生的。Git 的版本有语义：主动 commit，写 message、选分支、打 tag，"修复登录 bug"和"升级依赖"是两个意思不同的版本。历史是可以阅读、可以回溯、可以 cherry-pick 的。对象存储的版本没有语义：每次写入自动生成一个版本，version ID 是系统分配的一串随机字符，与内容无关，没有作者、没有说明、没有分支。只能按时间或 ID 取回，无法表达"这是一次有意义的变更"。

区别三，有没有分支与合并。这是两者最大的不同。Git 的全部协作能力，分支、合并、冲突解决、rebase、blame、bisect，都建立在 DAG 历史上。对象存储没有这些：两个客户端同时写同一个 key，后写的直接覆盖，或者产生两个版本，没有合并的概念，也没有冲突需要解决。它只有"删除标记"（delete marker，逻辑删除）和生命周期规则（旧版本多少天后过期）。

区别四，寻址方式。Git 是内容寻址：地址就是内容本身的哈希，相同内容天然去重，改一个字节地址就变，历史防篡改。对象存储是 key 加 version ID 寻址：key 是你起的名字，version ID 是系统随机分配的。S3 也有 ETag（内容的 MD5），但它只是校验和，不是版本标识。

区别五，分布式 vs 中心化服务。Git 每个 clone 都是完整副本，离线可用；对象存储是中心化的服务，即使底层多副本，用户看到的也只是一个逻辑桶，必须联网通过 HTTP API 访问。

两者结合的形态也已经出现了：LakeFS、Nessie 这类系统直接把 Git 式的分支、提交、合并语义搬到对象存储上，让数据湖也能像代码一样做分支实验和合并。

最后总结一句我自己的理解：Git 是给人协作演进内容的版本管理，对象存储的版本管理是给数据做保护和恢复的。前者关心"这次改了什么、为什么改"，后者只关心"别丢、能找回"。

## 十、一个提醒：进了历史的东西很难真正删掉

Git 保存了完整历史，一旦密码、密钥、令牌这类敏感信息被提交进去，即使后面删掉了文件，它还留在历史里的某个提交上，任何拿到仓库副本的人都能找出来。

想彻底删掉，要改写整个历史，生成一组不含这些信息的新提交，再强制推送，还要所有协作者重新克隆。代价很高，而且拿不回已经被别人取走的副本。所以一旦泄露，第一件事是让泄露的东西失效，比如换密码、吊销密钥，而不是只想着从历史里删掉它。

平时预防更重要：敏感配置文件用 .gitignore 排除，提交前用工具扫一遍。

## 写在最后

整理完这些，我自己再敲 git 命令的时候，感觉清楚多了。git add 是写 blob、git commit 是打包快照、git branch 是写指针、git fetch 是同步对象、git push 是请对方移动指针；merge 是找共同祖先做三方比较，rebase 是把提交一个个重新应用成新对象。命令还是那些命令，但知道它们在干什么了。

上面这些都是我查资料加自己理解整理出来的，肯定有不严谨的地方，欢迎大家指正。
